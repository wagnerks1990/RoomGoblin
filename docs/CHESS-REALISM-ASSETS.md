# Realistic virtual chess: asset research

Research date: 18 November 2026. This is a source and implementation plan, not an imported asset pack or a production change. Only this document was added for this research. No model archive was downloaded, executed, purchased, accepted through an account, or added to a SCORM package. Therefore archive contents, embedded textures, hashes, skeletons and actual browser appearance remain unverified.

The practical route to more convincing stone warriors is detailed humanoid anatomy and armor, restrained stone materials, grounded motion and lighting. Larger procedural shapes alone will not produce film-quality characters. Use original art direction rather than reproducing movie characters, uniforms, sets, audio or capture choreography. Preserve the existing server-owned game and optional 2D fallback.

## Recommended routes

**Best control over the final animated cast:** generate a clothed humanoid from MakeHuman's bundled CC0 assets, add original armor and six recognizable role silhouettes in Blender, then rig/retarget permitted animations. This involves character art and animation work; it is not a finished high-detail chess set. The project explicitly distinguishes its AGPL program code from CC0 graphics/output and warns that community downloads can have separate licenses. Import generated graphics only, not program code into the browser. [MakeHuman's official license](https://github.com/makehumancommunity/makehuman/blob/master/LICENSE.md) and [asset license](https://github.com/makehumancommunity/makehuman/blob/master/LICENSE.ASSETS.md).

**Fastest detailed visual prototype:** use the specific Poly Haven Gothic Statue below as a static hero on a test board, with local stone textures and lighting. It can establish the desired appearance before spending time on a full rig. Its robe, sculpted pose and joined surfaces mean walking requires substantial retopology, segmentation and rigging; translating a rigid scan is not a believable human walk. Do not promise this static asset already provides animated combat.

**Fastest rigged motion prototype:** Quaternius' explicitly CC0 knight and animation packs have useful skeleton/motion sources, but their character style does not meet a photorealistic target. Use them to test retargeting, footprints and capture timing while the detailed cast is authored. Do not describe a stylized character substitution as the realism milestone.

## Sources excluded from copying

The user-referenced [UFMiDAS2020/WizardsChess repository](https://github.com/UFMiDAS2020/WizardsChess) demonstrates a Unity/Oculus VR approach. Its reviewed root listing has no license file or reuse grant. Public GitHub visibility does not authorize copying the code, Maya art, textures, wizard hat or bundled third-party packages into RoomGoblin. Use it only as a design reference unless an explicit applicable grant is verified. Its Unity/Photon implementation is also a different runtime from the browser renderer.

A generic marketplace “free” or “royalty-free” label is insufficient for a repository and SCO that distribute extractable model files. Film rips, unclear mirrors, noncommercial/editorial-only assets, and packs restricting standalone/raw redistribution are outside this plan. Mixamo or paid Unity/Fab packs are not approved sources here; neither their current terms nor per-asset redistribution permission were reviewed for this task. No account signup, purchase or license acceptance has been performed.

## Proposed local runtime budget

These are initial engineering targets, not measured performance claims. Profile a complete 32-piece board on an actual school computer and a modest mobile device before settling them.

| Budget | Initial target |
| --- | --- |
| Character geometry | LOD0 around 8K–12K triangles per normal piece; six shared role meshes, not 32 separately authored files. About 300K–400K visible scene triangles including board/props; optional higher-detail close-up only when few pieces are rendered |
| Draw work | Aim below 150 draw calls in normal play; shared materials/atlases and merged rigid armor. A skinned character has its own skeleton state even when geometry is shared |
| Animation | Roughly 40–65 deform bones per character; update only required moving/reaction pieces at full rate. Keep distant idle characters in held or low-rate poses; animate only confirmed adjacent server revisions |
| Textures | Shared stone material and compact role atlas, typically 1K with selective 2K hero detail; avoid six independent 8K map sets. Measure decoded GPU memory, not ZIP size |
| Transfer | Aim for at most 15–25 MB of optional optimized character assets for the whole cast; load on explicit 3D selection. Do not delay the playable 2D board or initial SCORM connection |
| Frame behavior | Target steady 30 fps on a modest school device; permit 60 fps on capable machines. Cap pixel ratio, use one bounded shadow map, reduce effects/shadows under load and preserve instant 2D escape |

Do not assume 32 copies of the 28K statue or 120K museum model are inexpensive because a single asset displays well. The counts, texture memory, skinning and shadow passes all matter. Use LODs and reusable art rather than increasing every primitive's subdivision count.

## Implementation and release plan

1. Choose **one** legally documented body/armor source for a visual proof. Preserve source URL, author, exact license text, download date, archive file list and SHA-256. Stop if the archive adds terms inconsistent with public/raw redistribution. Do not execute downloaded scripts or Blender startup handlers.
2. Inspect the source mesh and textures offline. Establish six legible silhouettes: infantry pawn, fortified guard rook, mounted or horse-crested knight, robed bishop, crowned queen and king. Use original accessories and clear team material contrast. Avoid relying on a face or small emblem to distinguish a role.
3. Retopologize/rig, bake stone detail into normal/roughness maps and create LODs. Author or retarget permitted motions. A capture should have anticipation, a short readable action and a non-graphic stone defeat; avoid lengthy sequences that conceal the board or hold the turn hostage.
4. Export a self-contained **GLB** per role/asset group with embedded local textures and selected animation clips. Remove cameras, unused animation tracks, hidden geometry and external URL references. Inspect the resulting GLB rather than trusting a successful exporter dialog. glTF loading and animation use the existing pinned local Three.js version; see [official Three.js documentation](https://threejs.org/docs/).
5. If compression is used, bundle the exact compatible decoder locally with its notices. Do not introduce a CDN, runtime asset marketplace, external analytics or credentials. Include every needed file in fresh SCO exports and manifest coverage. Teacher assets remain gateway-denied; the SCO receives its own packaged presentation assets.
6. Keep server moves/results authoritative. Loader failure, context loss, late assets, revision gaps, a different selected game or reduced motion must snap safely to the current confirmed state or return to 2D. Destroy mixers, skeleton resources and GPU allocations when leaving 3D; never accumulate a renderer on every toggle.
7. Validate unique controls and actual application styles, 32-piece performance, shadow cost, orientation, promotion, castling/en passant, capture cancellation, high contrast, mobile touch and keyboard fallback. Record FPS/frame-time, draw calls, triangle count, transfer/decoded memory and load time. Test an exported ZIP with networking disabled for local assets, then perform separate live Schoology acceptance.

No candidate here is certified film-quality, game-ready or fully cleared by an archive inspection. The first implementation milestone should be a demonstrably detailed and performant **single** stone warrior under the real renderer, followed by a coherent six-role cast and its verified motions. Further production release needs its own review; this research does not alter the earlier chess release.

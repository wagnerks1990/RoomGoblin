# Chess engine, isolation and lifecycle review

Review date: 18 November 2026. Scope: the teaching worktree, server chess rules and saved histories, queues/clocks, original assignment scope, results, hints and SCORM export/resume boundaries. This is a code and synthetic-regression review, not live Schoology, production, classroom GPU or exhaustive FIDE certification. No production data was changed or deleted.

## Confirmed findings and changes

| Severity | Reproduced behavior | Narrow correction and evidence |
| --- | --- | --- |
| P2: saved history omitted | A participant's 105 newer results in another assignment hid a saved result in the requested assignment because the query limited rows before applying assignment scope. | Apply the original white/black assignment predicates in SQL before the 100-result bound. The regression failed before the change and passes afterward. No account or assignment access is expanded. |
| P2: active monitoring omitted | 205 recent finished games hid an older active game from the teacher control center. | Fetch all admitted open games (bounded at 250) separately from the most recent 100 finished games. Existing active games remain visible regardless of finished history size. No active game expires or changes status. |
| P2: resumed queue omitted | An old queue with a fresh owner heartbeat was hidden behind 105 newer but stale queues because filtering followed a 100-row cutoff. | Inspect the entire bounded 250-open-game candidate set before seat-access and 35-second freshness checks. Automatic matching and explicit joining still require freshness and assignment availability. |
| P2: draw bypassed unavailable opponent | A participant could offer or accept a draw after the other seat's assignment had closed, although moving was correctly blocked. | Draw actions now recheck both original seats' availability inside their transaction before claims or agreements. Tests cover closed cross-class offer and acceptance without changing the match. The existing active-player revision and draw-offer lifecycle checks remain in place. |
| P2: repeated polling work | Every render reconstructed legal history to calculate claims, even when a final-state cache existed. Clock or offer revision changes also invalidated the old state cache despite unchanged moves. | Cache final state and claim flags against exact saved move JSON. Never retain historical board arrays, names, authorization, grades, clocks or viewer projections. Bounds are 400 entries and 100,000 total cached plies, covering a 350-row teacher working set at 200 plies/game without entry thrashing. Tests exercise invalidation, fresh aliases and both memory budgets. |
| P3: growing-table scans | SQLite query plans showed a full match scan for owner/assignment lookup, and a full presence scan plus temporary sort for recent connections. | Add non-destructive white-owner/assignment, black-owner/effective-assignment and last-seen indexes. Query plans now use `MULTI-INDEX OR` with scoped searches and an indexed presence range. Source compatibility identifiers and persisted results are unchanged. |
| P3: repeated roster reads | Seat availability and direct-owner availability loaded the entire user inventory to find one account. Repeating these checks for queues/clocks multiplied work by unrelated account count. | Read only the target account's six needed public/security fields through its indexed ID. No authorization result is cached. Regression checks retain immediate disable/re-enable/class-revocation behavior and fail closed on malformed owner settings. |

`test/learning-chess-engine-review.test.js` contains the reproductions. Its first four tests were executed against the prior source and all four failed, establishing the visible defects before correction. The review does not change the server move validator, widen the learner gateway, reset games, merge LMS accounts or add a new production dependency.

## Performance evidence

An external synthetic benchmark generated the same deterministic legal 200-ply position, warmed the cache once, then rendered it 100 times in the active Windows worktree using Node 24.15.0 and an ephemeral local fixture. Before the projection-cache change it took **559.36 ms** total; afterward **2.59 ms** total in one local run (approximately 5.59 versus 0.03 ms/render). These are illustrative local measurements, not a hardware-independent speed guarantee or classroom acceptance. No timing threshold was added to tests.

The cache contains only viewer-independent rule projections derived from the saved server match; a private practice position does not become public. Each API request still performs current authorization; each render still projects names, teacher membership, own-seat fields and clocks from current data. Cached rule values are invalidated by exact move text, including a change that does not happen to advance a revision. Clock/draw-only revisions can safely reuse that rule projection. All move histories remain durable in SQLite; eviction removes only transient acceleration data.

The original owner queries and recent-presence queries were inspected with SQLite `EXPLAIN QUERY PLAN` before and after the additive indexes. Index changes require the usual backed-up, reviewed release path; no production migration was run as part of this review.

## Rules and transaction checks

The focused suite retains initial/castling-rich move-tree counts, both colors/sides of castling, attacked versus occupied transit paths, lost castling rights, pinned and horizontal-discovery en passant, four promotions, king safety, mate/stalemate and repetition identity. Claimable threefold/50-move thresholds remain separate from automatic fivefold/75-move endings, with mate precedence. The official reference and physical-tournament exclusions remain in [the rules audit](CHESS-RULES.md).

Computer search remains in bounded workers, outside SQLite transactions, with saved revision/access rechecked before commit. Duplicate same-revision searches are rejected, and a later resignation or unavailable assignment cannot be overwritten by a delayed search. Human and computer moves remain one authoritative committed result. Search failure leaves the board unchanged; clients must refresh rather than replay uncertain writes.

Clocks use saved server wall-clock anchors and increments, not browser countdowns. Unavailable seats pause reconciliation; restored seats resume from the saved balance. Clock processing respects writer-freeze/shutdown admission. Existing tests cover one-time timeout, disabled-seat pause/re-enable and prevention of subsequent moves after a terminal result. Reliable system time and the documented reconciliation/downtime behavior remain necessary.

## Isolation, hints and SCORM

Both sides retain their original activity scope after universal matchmaking. A bearer for a different assignment cannot move, hint or claim an existing private seat. Reported Schoology names/IDs remain attribution, not verified identity; separate participants are never merged by name. Full teacher aliases require membership in the corresponding class, and TV/student standings keep first name plus last initial with an allowlisted public result projection.

Practice explanations accept only a saved revision, derive legal examples from the saved position and deny all multiplayer or spectator requests. They recheck enabled/revoked accounts, assignment availability and computer-human turn state. Per-learner request windows and the limiter's total entries remain bounded. Hints do not mutate moves, grades, attendance or standings. Exact POST-only learner allowlists remain the only direct hint extension.

Chess packages contain their local board, coach, optional renderer and notices. The private participant credential resumes through LMS suspend data, and actor changes clear the previous learner's projections. Synthetic browser checks cover private enrollment/resume, failed grade-save retry and review mode; live Schoology acceptance remains separate. A SCORM browser's raw LMS score is still client-reported, not a cryptographic proof of untampered work. Competitive game results and the global leaderboard continue to come from server-owned moves and endings. No reported SCORM field authorizes physical attendance or room effects.

## Lifecycle contract and remaining work

Connection presence, matchmaking freshness and a saved active game are separate facts. An offline opponent is not a forfeiting opponent. Untimed active games remain resumable until a valid ending or a seat's explicit forfeit; this review never automatically deletes or forfeits them. Waiting queues do not contribute competitive results. Existing account/assignment deletion contracts remove related records; ordinary updates do not reset them.

The teacher control center now receives global and own-seat totals (`waiting`, `active`, `finished`, `mineWaiting`, `mineActive`, `mineFinished`) plus the returned/total counts and 100-result history bound. Teacher rows expose `queueFresh`; `canCancelQueue` is true and `cleanupClassId` is populated only for a waiting queue whose original white class the teacher is authorized to manage. Membership and permission are checked again when acting; presentation flags never authorize a write.

Join affordances now reflect actual queue freshness and white-seat availability, rather than inviting a teacher to join an offline or closed request that the endpoint would reject. Freshness is a recent heartbeat/create signal, not proof of a continuously connected device.

The manual endpoint `POST /api/v1/learning/teacher/classes/:id/chess/matches/:matchId/cancel-queue` accepts exactly `{revision}`. It requires normal teacher login and the original white class's teacher membership. Only an unjoined waiting row at that revision can change. Cancellation retains the record with `queue cancelled`, adds one audit event atomically, releases open-game capacity and contributes no competitive result or participation. Closed-assignment queues can be removed by their teacher without reopening student writes. The SQL status/revision fence prevents cancellation racing past a join; audit failure rolls the cancellation back. Export freeze rejects the HTTP action. No direct/student-gateway route, learner permission or new schema was added for this action.

The following remain explicit limits or follow-up work:

- The cache does not solve all growth: finished results and presence records persist, standings aggregate all retained finished results, and accepted moves/intended draw claims can still replay a long saved history. More aggressive summaries or retention need separate correctness, deletion and privacy proofs.
- The API returns bounded recent history, not an exhaustive paginated archive. Global standings currently return the top 100 accounts, rather than paginating every retained player. Teacher waiting-only cleanup does not imply authority to forfeit active games or erase another class's data.
- Completely arbitrary dead positions and every possible cooperative mating scenario are not exhaustively solved. The existing conservative proofs and documented limitations remain.
- Classroom time controls still depend on the server clock. A backup freeze, process interruption, manual clock correction or delayed availability reconciliation has the behavior documented in Chess Arena; browser estimates cannot resolve those cases independently.
- A bounded system sweep expires only unjoined, zero-move multiplayer waiting requests after 24 hours without a queue update or an owner heartbeat for the original assignment. It runs at most once per minute under the existing writer-freeze/shutdown guard; at most 250 rows are considered. The revision/status fence and system audit are transactional; audit failure rolls back the entire sweep and remains visible through service availability. Rows and creation-idempotency records remain intact (`queue expired`, null result), freeing capacity without adding leaderboard results. Reusing an old creation request ID returns the retained expired request; a new game needs a new request ID.
- Automatic deletion, active-game inactivity penalties, arbitrary database cleanup and silent archival have not been added. Active untimed games remain resumable regardless of offline age. Future retention changes must preserve results and rollback and keep cross-class and export-freeze boundaries.
- Live LMS, real school devices, large retained datasets and deployed acceptance remain unverified by these local tests.

## Validation status

The combined release passed all 90 chess automated tests, including cleanup, scope, hints, rules, package manifests and motion regressions. Five Edge browser suites passed 56 checks: legacy SCORM 9, interaction/3D/TV 9, coach/SCO 18, UX/lifecycle 10 and direct-assignment 10. The final coach, UX and SCORM suites were rerun after queue expiry was integrated. Standalone cinematic checks also passed. These use synthetic local services and LMS fixtures, not live Schoology or school devices.

The supported full Linux regression runner is required against the combined release before merge; its final result is recorded in the release pull request. The earlier teaching-only snapshot passed 3,067 tests with two existing root-only backup-permission skips, but that result does not certify the later integrated cinematic and queue-cleanup changes. Deployment requires exact published image revisions, a verified operational backup, preserved records and healthy services; a merged PR alone does not establish deployment.
